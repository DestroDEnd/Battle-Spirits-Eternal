# 4. PHASE C — DIRECT COMBAT RESOLUTION AUTHORITY

**Priority: CRITICAL**

Primary files:

- `engine/response_window.js`
- `engine/index.js`
- `engine/windows.js`
- `engine/action_authority.js`

### C1. Guard resolveBattleComparison()

The current public method:

`ResponseWindowManager.resolveBattleComparison(win)`

can be directly invoked while Flash 2 is active.

It currently resolves BP comparison even though the active window has not closed.

Correct this.

The only authorized path to comparison must be:

1. Defender declares a legal block.
2. When Blocks effects resolve.
3. Flash 2 opens.
4. Defender receives first priority.
5. Players alternate priority legally.
6. Two consecutive passes close Flash 2.
7. The authorized close-window lifecycle invokes BP comparison.

A direct call from an arbitrary caller must not bypass these conditions.

### C2. Separate internal resolution from public entry points

Do not merely check whether a window exists and assume that the current caller is authorized.

Implement a trusted internal resolution boundary.

Possible approaches include:

- A private/internal resolver method.
- A validated closed-window reference.
- A trusted internal resolution capability or equivalent ownership mechanism.
- A state-machine transition that only the response-window manager can initiate.

Use the cleanest compatible architecture.

The internal caller must prove that:

- The relevant window is the correct Flash 2 window.
- The window closed through the authorized two-pass path.
- The block remains valid.
- The associated combat still exists.
- The attacker and blocker references still match.
- The same battle has not already resolved.

Prevent duplicate or replayed BP comparison.

### C3. Audit all combat resolution methods

Review:

- `declareAttack`
- `declareBlock`
- `resolveDirectHit`
- `resolveBattleComparison`
- `endBattle`
- `endAttack`
- `closeWindow`
- `onWindowClosed`
- `handleBlockDeclaration`
- `handlePassBlock`
- `passPriority`

Look for:

- Public methods that invoke internal resolution without authorization.
- Duplicate state transitions.
- Premature window closure.
- Incorrect priority ownership.
- Resolution after combat has already ended.
- State mutation before validation.
- Window-stack inconsistencies.
- Direct life damage without a valid block decision.

### C4. Preserve approved combat lifecycle

Do not change the current intended M3.2 response lifecycle without authoritative rules evidence.

Preserve:

**Blocked combat:**

`ATTACK → WHEN_ATTACKS → FLASH_1 → BLOCK_DECLARATION → WHEN_BLOCKS → FLASH_2 → BP_COMPARE → BATTLE_END`

**Unblocked combat:**

`ATTACK → WHEN_ATTACKS → FLASH_1 → BLOCK_DECLARATION → PASS_BLOCK → DIRECT_HIT`

The current design skips Flash 2 after PASS_BLOCK. Preserve this established project behavior unless an authoritative Eternal rules source in the project demonstrates otherwise.

Preserve defender-first priority, alternation, consecutive-pass closure and non-forfeiture of future opportunities.

### Required tests

Create:

`tests/phase_m3_3_combat_resolution_authority.test.js`

Actually invoke every protected method.

In particular, the test for BP comparison must directly invoke `resolveBattleComparison()` while Flash 2 is still active and assert that:

- It fails.
- Combat remains unchanged.
- Both units remain on their respective fields.
- No BP comparison event is emitted.
- Flash 2 remains open.

Then test the legitimate closure path and prove that BP comparison executes exactly once.
