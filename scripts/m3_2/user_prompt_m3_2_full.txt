# PHASE B — UNIVERSAL RESPONSE WINDOW ACTION AUTHORITY

This is the highest-priority work package.

The active response window must completely control which player can act and which actions can be performed.

## B1. Centralized action authorization

Create or refactor a central authorization mechanism used by BOTH:

1. `BattleSessionManager.submitPlayerAction()`
2. Direct engine action methods in `engine/index.js` and `engine/response_window.js`

Do not maintain two independent and contradictory authorization systems.

Every state-changing action must pass through authoritative validation.

Audit at minimum:

- `STEP_ADVANCE`
- `ADVANCE_STEP`
- `ATTACK`
- `PLAY_CARD`
- `SUMMON`
- `SET_BURST`
- `USE_CORE`
- `END_TURN`
- `ACTIVATE_ABILITY`
- `USE_ACCEL`
- `FLASH_ACTION`
- `CAST_FLASH_MAGIC`
- `DECLARE_BLOCK`
- `PASS_BLOCK`
- `PASS_PRIORITY`
- `INTERACTION_RESPONSE`
- Other existing action types capable of changing game state.

Do not assume that protecting the REST endpoint automatically protects the engine.

Direct method calls must also be safe.

## B2. While a response window is active

The engine must enforce these rules:

- Only the current priority holder may submit a response.
- Only actions permitted by the active response-window type may be performed.
- The non-priority player cannot perform ordinary game actions.
- The turn player cannot bypass the window by submitting `PLAY_CARD`, `SUMMON`, `USE_CORE`, or another action under a different action type.
- Players cannot declare another attack during an active combat response window.
- Players cannot advance the game step while a response window is unresolved.
- Players cannot invoke direct block or battle-resolution methods to skip the response lifecycle.
- A client cannot invent an action name, interaction ID, decision owner, card ID, or response type to bypass authorization.

Validate the actual authenticated participant, not a client-supplied player identity.

Return consistent errors such as:

- `RESPONSE_WINDOW_ACTIVE`
- `NOT_PRIORITY_PLAYER`
- `ACTION_NOT_ELIGIBLE_IN_WINDOW`
- `INTERACTION_NOT_PENDING`
- `INVALID_CANDIDATE`
- `FLASH_TIMING_NOT_OPEN`

## B3. Preserve legitimate opponent responses

Do not implement a simplistic rule that blocks every action from the non-active player.

The defending player must be allowed to perform legitimate actions when:

- They hold priority during Flash Timing.
- They own a pending interaction.
- They are entitled to declare a blocker.
- They are responding to an effect or decision that explicitly assigns them responsibility.

The active player must also receive priority when the response-window rules assign it to them.

The authorization policy must depend on the current engine state and the actual action type.

Fix the underlying engine methods so that they cannot independently bypass the response-window lifecycle.

- Any other methods that can advance or resolve combat.

## C1. Block declaration

A block must only be declared through an authorized `BLOCK_DECLARATION` window.

The defender must hold the appropriate decision ownership and priority.

Remove any implementation that allows `declareBlock()` to close `FLASH_1` and skip the remaining Flash Timing.

The only valid sequence is:

`FLASH_1 closes → BLOCK_DECLARATION opens → Defender declares block → WHEN_BLOCKS triggers resolve → FLASH_2 opens`

## C2. Passing block

The defender must explicitly choose `PASS_BLOCK` or the appropriate no-block action.

Only after a valid defender decision may the engine skip Flash 2 and resolve an unblocked attack.

Calling `resolveDirectHit()` directly must not allow a caller to bypass the defender's mandatory block decision.

Respect mandatory blocking rules such as `mustBlockIfAble`.

## C3. Battle comparison

BP comparison must not happen merely because a block was declared.

It must occur only after:

1. A valid block declaration.
2. All relevant `WHEN_BLOCKS` triggers have completely resolved.
3. Flash 2 has opened.
4. Both players have passed consecutively and Flash 2 has legitimately closed.

Do not allow direct calls to `resolveBattleComparison()` to circumvent this sequence.

Preserve existing battle-resolution mechanics, BP modifiers, destruction rules, prevention effects, and state-based actions.

## C4. No premature window closure

Do not close an active window merely because a different method was called.

Window transitions must occur through the authorized response-window lifecycle.

# PHASE D — FLASH ACTION EXECUTION INTEGRITY

This work package is particularly important.

Currently, `ResponseWindowManager.handleFlashAction()` executes the requested action but does not consistently inspect the underlying action result before resetting consecutive passes and alternating priority.

This must be fixed.

## D1. Validate before execution

Before executing a Flash action, verify:

- The current response window is open.
- The caller holds priority.
- The requested action is permitted by the window.
- The submitted card or ability exists.
- The card belongs to the submitting player and is in the correct zone.
- The ability exists and is physically addressable.
- The card's Flash timing restrictions permit activation.
- The player's current game state permits activation.
- Costs can be paid.
- Candidate membership and all restrictions are satisfied.

## D2. Validate the execution result

After execution, inspect the actual result returned by:

- `game.playCard()`
- `game.activateAbility()`
- `game.executeAccel()`
- Other supported Flash action handlers.

Do not treat an unsuccessful execution as a successful Flash.

A failed action must NOT:

- Reset consecutive passes.
- Alternate priority.
- Add a successful Flash entry to response history.
- Consume a card or cost.
- Close the current window.
- Create an event representing a successful activation.

Only a successfully committed Flash action may reset consecutive passes to zero and alternate priority.

## D3. Safe rollback

If an action fails after partially mutating game state, restore the previous valid state without creating inconsistent events or costs.

Preserve M.2's transactional persistence guarantees.

Do not broadcast a successful action event before the authoritative commit succeeds.

# PHASE E — CORRECT FLASH TIMING MODEL

Remove the incorrect assumption that every Flash effect is restricted to the Attack Step.

The authoritative Flash timing model must distinguish:

1. Generic Flash effects.
2. Card-specific Attack-Step restrictions.
3. Event-triggered Flash effects.
4. Flash Timing-only effects.
5. Flash effects requiring an active battle.
6. Main Step and Attack Step timing.
7. Turn-owner restrictions.

Use the existing `engine/flash_timing.js` architecture, but correct the implementation comprehensively.

## E1. Generic Flash

A generic Flash effect without an explicit narrower timing restriction is available:

**During the controller's Main Step**
- Only the active player can use it.
- The active player pays the required cost.
- The effect resolves normally.
- The active player retains initiative.
- No artificial opponent response window is created.
- The player may continue performing normal Main Step actions.

**During battle Flash Timing**
- Both players can use legal generic Flash effects when they hold priority.
- The normal response-window lifecycle controls the action.
- After successful resolution, priority alternates.
- Consecutive passes reset to zero after a successful Flash.

A generic Flash effect must NOT be globally restricted to the Attack Step.

## E2. Card-specific restrictions

Explicit card text overrides generic Flash availability.

Implement and verify these categories:

| Card timing qualifier | Permitted timing |
|---|---|
| Generic Flash | Controller's Main Step and either player's battle Flash Timing |
| `(Your Attack Step)` | Only the controller's Attack Step |
| `(Opponent's Attack Step)` | Only the opponent's Attack Step |
| `(Either Attack Step)` | Either player's Attack Step |
| `During Attack` | Only during a qualifying active battle and permitted Flash Timing |
| `During Flash Timing only` | Only an active battle Flash Timing window |
| `(When Attacks) Flash` | Event-triggered resolution upon the applicable attack event |

Do not assume that similar-looking text always represents the same timing rule. Confirm the exact semantics against the existing card corpus and the official rules already referenced in the project reports.

## E3. Turn ownership

For a card controlled by Player A:

- `(Your Attack Step)` is legal when Player A is the attacking turn player.
- `(Opponent's Attack Step)` is legal when Player B is attacking and Player A is defending.
- `(Either Attack Step)` can be legal during either player's Attack Step, subject to actual Flash Timing priority.
- `During Attack` requires the specified battle context.
- `During Flash Timing only` must not be available outside an active Flash Timing window.

A valid game step alone is not sufficient to authorize an Attack Step Flash.

The player must also have actual response-window priority.

## E4. Triggered Flash

`(When Attacks) Flash` must be classified as an event-triggered effect when that is what the card specifies.

It must:

- Resolve through the trigger system at the correct timing.
- Not appear as an ordinary voluntary Flash action.
- Not be manually activated as a free Flash.
- Not be rejected by the legacy blanket Attack-Step-only guard before trigger classification.
- Resolve in the correct order relative to other attack triggers and Flash Timing.

Do not confuse a triggered effect with a voluntary Flash activation.

# PHASE H — RESPONSE WINDOW PRIORITY AND LIFECYCLE

Preserve the existing M.3 architecture and correct its implementation.

The authoritative Attack Step battle sequence must be:

1. Attack declaration.
2. `WHEN_ATTACKS` triggers resolve completely.
3. Flash Timing 1 opens.
4. Defender receives first priority.
5. Priority alternates after a pass or successfully resolved Flash.
6. Flash Timing 1 closes only after two consecutive passes.
7. Block Declaration opens.
8. Defender chooses a legal blocker or explicitly passes.
9. If a block is declared, `WHEN_BLOCKS` triggers resolve.
10. Flash Timing 2 opens.
11. Defender receives first priority.
12. Priority alternates after a pass or successful Flash.
13. Flash Timing 2 closes only after two consecutive passes.
14. BP comparison and battle resolution occur.

If the defender passes block:

- Skip Flash Timing 2.
- Resolve the unblocked attack and corresponding life damage.
- Preserve relevant damage prevention, must-block restrictions, and other card effects.

## H1. Non-forfeiture rule

Passing once must not permanently surrender a player's opportunity.

Example:

1. Defender passes.
2. Attacker receives priority.
3. Attacker plays a successful Flash.
4. Consecutive passes reset to zero.
5. Priority returns to defender.

The defender must be able to respond again.

## H2. Failed Flash attempts

If a player attempts an illegal Flash:

- Do not consume priority.
- Do not reset the pass counter.
- Do not change the response-window owner.
- Do not consume resources or the card.
- Return an explicit failure reason.

## H3. Trigger execution

`WHEN_ATTACKS`, `WHEN_BLOCKS`, and other relevant triggers must resolve completely before the applicable Flash window opens.

A Flash must never interrupt an already resolving effect.
