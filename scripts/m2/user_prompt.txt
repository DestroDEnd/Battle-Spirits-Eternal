# 1. MISSION

Phase M.1 implemented persistent multiplayer sessions, SQLite-backed state, reconnection, connection leases, and real-time synchronization.

An independent audit subsequently reproduced three critical defects:

1. Raw player authentication tokens are included in serialized game-state snapshots and exposed through the match-state API.
2. A player can submit an action using a valid token even when that player is not authorized to act during the current game phase.
3. Failed actions are written to the action ledger before execution succeeds, causing legitimate retries with the same action ID to be rejected as duplicates.

A further security issue was identified in the active-match and match-history endpoints: they trust a caller-supplied `playerId` without authenticating the caller.

Your task is to correct these defects at the architectural level, not merely patch the individual reproductions.

**Do not rebuild Phase M or M.1. Preserve the existing persistent-session architecture and make targeted corrections.**

- No raw authentication credentials in game-state snapshots, database snapshots, events, or client responses.

- Atomic state/action/event persistence.
